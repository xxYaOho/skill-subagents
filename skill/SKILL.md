# Yes! Subagents

将低价值、且极耗上下文的"累活脏活"留在子代理的会话空间里，你只关注高价值结果，保持自身上下文健康。

快速开始：

- 检查当前可被派遣使用的子代理列表;
- 主动派遣与 `subagents/` 中名称及用途一致的子代理;
- yes-subagents 的子代理与工具内置子代理职责重复时, 优先派遣内置子代理 (内置子代理可能与工具本身适配更好)；在派遣时必须在指令中注入本 skill 的统一输出契约（PRECONDITION 前置检查、Output exactly 分节要求、STATUS 结尾），确保产出都能按同一标准解析与判断。若工具的系统级格式与该契约冲突，尽力遵循，至少保留 STATUS 行。

子代理：

1. 监察类
   - Critic Strict：审查会被后续决策依赖的方案、计划或结论；完整契约由 `subagents/critic-strict.md` 持有
   - Critic Gate：核验实现是否忠于有效基线、有无回归与契约破坏；完整契约由 `subagents/critic-gate.md` 持有
2. 调查类
   - Quality Auditor：核查存量代码质量与技术债务，不绑定某次具体变更
   - Debugger：复现、定位、给出根因，只诊断不修复
   - Researcher：探索、检索与定位，产出结构化结论而非原始堆砌
   - Scout：核验 Pruner 提出的清理目标是否真的可安全删除或合并，只读，只判定安全性不判定是否值得清理；完整契约由 `subagents/scout.md` 持有
3. 行动类
   - Swarm：执行简单、同质、边界明确的工作单元；可单体、普通并行或作为蜂群成员派遣
   - Coder：执行需要跨文件推理、项目约定或需求质疑的工作单元；可单体、普通并行或作为蜂群成员派遣
   - Pruner：编码任务全部里程碑完成后，清理本次任务触及文件中的冗余与残留；行动前须经 Scout 核验，执行后不回退到 Critic Gate 复核；完整契约由 `subagents/pruner.md` 持有

> **豁免**
> 简单到极致或偏日常的工作，不派遣子代理。例如：修改几行代码、确认项目版本号; 询问时间天气、日常问候

## 编排核心

### 组合

组合是所有任务都具备的基础编排能力，不是可选模式。根据目标组合调查、行动和监察职责，可串行，也可并行。简单一次性任务仍由主代理直接完成。

单个会话视角总是有限。需要多元视角、独立调查或上下文隔离时，主动组合合适的子代理，而不是固定套用某条流程。

### 飞轮

```
Action
  ↓
Verify or Review  → Fix (max round: 10)
  ↓
Action Again
  ↻
```

`行动 --> 审查 --> 修正 --> 再行动` , 飞轮最多修正 10 轮；初始产出、蜂群分批和代理重试不计入修正轮次。

- 满足预定目标 (或 PASS) 后停止飞轮，将剩余非阻断问题一并汇报
- 达到最大轮次时停止飞轮, 向用户诚实汇报未完成根因

### 调度

- 1 个工作单元：单体派遣。
- 2–3 个独立工作单元：普通并行或组合派遣。
- 至少 4 个独立工作单元：考虑蜂群调度。

蜂群按任务所需的独立工作单元总数判断；重试、返工和分批不增加成员计数。并发不足时分批运行仍属于同一次蜂群。工作单元形成依赖链时改为串行，不再视为蜂群。

蜂群不绑定代理类型。简单、同质单元优先使用 `swarm`；需要工程推理的单元使用 `coder`；调查或监察代理也可组成蜂群。每个成员必须有明确职责、输入边界和输出契约。

### 待机

子代理运行在独立的上下文空间中，执行过程不进入编排者的上下文。派遣完成即工作交接完成：任务、边界与输出契约都已随派遣指令交付，之后以完成通知作为推进信号。

结束回合不终止任务：后台子代理完成时会重新唤起编排者，职责链的下一环由通知触发，不需要值守。等待期间的每次轮询都是一次完整的上下文载入，换回的只是「仍在执行」这类零信息结果，查询记录还会追加进会话历史。

> [!IMPORTANT]
> 严禁编排者为维持与子代理的关联而轮询、实时同步或自设定时唤醒。仅在用户询问状态、需要中断或追加指令、或收到异常通知时介入；其余情况一律等待完成通知。

## 验证与监察

区分视觉与工程的验收. 视觉与交互, 需要 user 的参与完成验收, agent 负责可被简单量化的结果复查, 例如颜色值, 功能数量, 文生图质量等等,  agent 不负责审美; 代码工程, 由 agent 完全负责, 例如自动化测试、类型检查、构建、契约测试或基准测试等等, 进行直接验证, 不为流程完整追加监察。

直接验证无法覆盖隐藏风险时，再选择监察代理：

- 想法、草案、报告或会被后续决策依赖的结论使用 `critic-strict`
- 计划是否使用 `critic-strict`，按对应 workflow 文件中的判断标准（如 `workflow/coding.md` 的「计划审查阈值」）决定
- 存在实现忠实度、回归、契约或隐藏正确性风险时使用 `critic-gate`
- 存在 `coder` 时, agent 可以主动担任 `critic-gate`, 而不必重新派遣

监察补充直接验证的盲区，不能替代测试、构建或真实渲染。完整审查契约由对应 subagent 文件持有。

## 审查与阻断

审查必须交给 fresh agent。不要 self-critique 自己的草案、方案、报告或实现；需要监察时，直接派遣对应 Critic。

派遣 Critic 后等待结果，不预判结论提前修改。若返回 `STATUS: BLOCKED`，先区分缺失项类型：

- 事实性缺失（文件路径、基线文档引用、上下文参数）：Orchestrator 可从现有上下文补全，原地重试一次。
- 判断性缺失（验收标准、目标边界、价值取舍的定义）：权威来源是用户，Orchestrator 不得自创。可以从上下文推导候选验收标准，但必须先交用户确认，确认后才能作为基线重新派遣。

执行代理的 `STATUS: DONE` 只表示工作单元完成，不代表整个任务完成。整个任务完成意味着直接验证足以覆盖主要风险并满足验收标准，或剩余风险对应的监察已返回 `STATUS: PASS`，而不是主观感觉“打磨够了”。

## 工作流

具体的阶段划分、里程碑推进节奏、每一步该派遣谁，按任务类型下沉到独立文件，避免每次派遣都要扫过与当前任务无关的流程细节.

- `workflow/coding.md` 适用范围: 编程, 开发等等工作
- `workflow/action.md` 适用范围: 无需计划草案的调查、诊断、行动类任务

## 严格禁止

- 严禁编排者为维持与子代理的关联而轮询、实时同步或自设定时唤醒。
