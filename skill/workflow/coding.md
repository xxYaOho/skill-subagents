# by Coding

适用场景：深入讨论后要求先产出草案/方案/计划，再进入实现的编码类任务。

每个阶段结束后默认停住等用户确认再进入下一阶段；若用户明确要求全自动执行（如"不用问我，全部做完再汇报"），则解除停顿。

本文件的每一步都在实例化 `SKILL.md` 中定义的飞轮原语（产出 → 验证 → 修正 → 再验证 → 停止，单次最多修正 10 轮）。下文在每一步标注它对应飞轮的哪一次运行、修正条件和停止条件，而不是抽象引用。

## 1. 前期讨论

形成会指导后续实现、包含隐藏假设或会被继续依赖的方案或计划时，派遣 `critic-strict` 审查，运行飞轮直到 `STATUS: PASS`（0 FATAL），再将最终输出给到用户。

**这是飞轮在讨论阶段的一次运行**：产出 = 草案/计划；验证 = `critic-strict` 审查；修正 = 根据 FATAL 反馈改稿；停止条件 = `STATUS: PASS` 或达到 10 轮上限。

纯视觉且可通过真实渲染直接验证的工作不为流程完整追加监察。计划类产出是否需要这一轮飞轮，按下面的判断标准决定。

### 计划审查阈值

计划不是草案的平凡投影：草案必然留空，计划必须做出生成性选择（步骤顺序、阶段边界、回退策略、验证方式），这些选择本身是未审查的假设。草案审查抓"想法错了"，计划审查抓"执行结构错了"，两者只在计划层很薄时重合。因此计划审查按厚度判断。

薄计划层（全部满足）可跳过计划审查：

- 生成性选择平凡：步骤顺序显然、单阶段、无需定义阶段边界、无回退/迁移/状态编排
- 改动可逆且局部
- 验收标准全部可直接验证
- 上游草案已通过 `critic-strict`（或改动小到无需草案）

任一命中则必须审查：

- 需要定义非平凡的阶段边界，或阶段间存在依赖执行顺序
- 计划做出草案留空的关键选择：回退策略、迁移路径、并发模型、验证窗口
- 不可逆或高爆炸半径操作
- 验证不透明（外部运行时、人工验收）
- 计划偏离已审草案——机械触发，不留裁量空间
- 无既有模式可循的新颖地带

跳过计划审查时必须显式声明理由（一行即可），向用户可见、可否决。厚度与改动规模无关：单文件改动若涉及数据语义选择（命名、编号、格式规则），仍属厚层。阈值只引用可观察的任务属性，不以改动规模或 agent 能力为依据。

典型边界：

- 视觉修改在真实页面或截图足以验收时跳过监察。
- 性能、数据、状态、接口、安全或无障碍语义存在隐藏风险时接入监察。
- 有自动化测试不代表自动豁免监察；测试可能未覆盖关键风险。
- 改动量大不代表必须接入监察；大量可直接验收的视觉修改仍可跳过监察。

### 讨论阶段的操作细则

- 分阶段实施的计划必须在进入实施前定义可验证的里程碑；每个里程碑节点文本必须自足：本节点验收标准编码对下游节点的接口承诺，并附下游对本节点的接口依赖——这是实施阶段派遣契约（`subagents/coder-plus.md`）的输入要求。具体审查与判定契约见 `subagents/critic-strict.md`。
- 修正轮次不超过 10 轮，避免沦陷在某个错误中无法离开，达到上限后主动停止飞轮并告诉用户具体情况。
- `STATUS: PASS` 后停止飞轮，将剩余 MAJOR/MINOR 一并汇报用户，由用户判断是否接受。
- 记录修正轮次。v1, v2... 不用体现在最终文件名中。
- 向用户输出时，除了完整的最终文档，(可选) 简要地说明迭代过程主要解决的问题点（偏低级错误就不说明）。
- **之后停止，等用户确认是否进入实施阶段。**

## 2. 中期实施

用户确认后进入实施阶段。实施以里程碑为单位推进，每个里程碑是一次独立的飞轮运行。

### 执行者分派

计划书已把工作切分为里程碑边界，分派按粒度机械判断，不再临时裁量：

- **里程碑节点**（含内部依赖结构的多个原子任务）：默认派遣 `coder-plus`，每个节点一次派遣。它是实施阶段的默认执行者。
- **单工作单元**（跨文件推理、需验证、无内部结构）：派遣 `coder`（单体或并行）。
- **独立同质单元批量**：按 `SKILL.md` 调度分档走蜂群。
- **平凡改动**（单文件级、直接可验证）：agent 亲自实施，用一行向用户声明理由。跳过派遣不豁免 gate。

### 派遣纪律

- 每次派遣只交出当前节点所需信息：节点实现内容、本节点验收标准、可动文件范围（里程碑边界）、下游节点对本节点的接口依赖摘要。其余节点的实现内容不外发——计划全文只存在于 agent，既防执行者预支后续里程碑，也避免重复加载。
- coder-plus 返回 `STATUS: DONE` 后依次收口：复核其 VERIFICATION → gate → PASS 后原子提交 → 才派遣下一个节点。派遣下一节点前，可依据上一节点的实际结果微调其节点文本。
- `Challenge before you build` 在开工时关闭：开工后节点文本即权威基线，coder-plus 无中途否决权；实现方式的裁量权归执行者，但偏差必须记入 DEVIATIONS。
- 完整契约见 `subagents/coder-plus.md`。

### gate：忠实度审查

gate 默认由 agent 亲自担任：忠实度审查依赖计划全文上下文，外派意味着重复加载；执行者是子代理，agent 审查他人产出，不属于 self-critique。两种情况派遣独立 `critic-gate`：

- 不可逆或高爆炸半径里程碑——机械触发，不留裁量空间。
- 其余里程碑存在直接验证未覆盖的回归、契约或隐藏正确性风险——agent 裁量。

gate 对照计划当前节点审查 DEVIATIONS 与 CHANGES，做偏差知情裁决：更优实现等良性偏差 + 验收满足 + 如实上报 = 可 PASS；偏离验收标准或中途削减范围 = FAIL。

- 外派时必须提供有效基线；基线选择与前置条件见 `subagents/critic-gate.md`。
- FAIL 的修正按偏差性质分流：原子性偏差（局部错误）派遣 `coder` 定点修正；结构性偏差（实现路线错误）重派 `coder-plus`。

**每个里程碑是飞轮的一次独立运行**：产出 = 该里程碑的实现（由 coder-plus 或 agent 亲自交付）；验证 = 执行者自验证（测试/构建/类型检查）+ agent 复核 + gate；修正 = 按 gate 裁决意见修正后重新审查；停止条件 = 该里程碑 PASS 且完成原子提交，随后进入下一个里程碑重新起算修正轮次。

- 里程碑边界应在前期讨论阶段随计划书一起确定，而不是执行时临时判断——执行者本身有把边界划大以减少被检查次数的动机，不适合让它自己决定检查点。
- **原子化提交是里程碑退出条件**：gate 返回 PASS 后，由 agent 以 Conventional Commits 提交该里程碑的全部改动（coder-plus 不创建提交）；用户未明确要求提交不构成跳过理由，未要求 push。
- 修正轮次不超过 10 轮，达到上限后主动停止飞轮并告诉用户具体情况。
- 最终完成计划书的所有事项，向用户汇报时，除了最终结果，(可选) 简要地说明过程中发现的重要情况，辅助设计决策（没有就不说明）。

## 3. 收尾整理

全部里程碑完成后，派遣 `pruner` 扫描本次任务触及的文件，起草清理计划（每项目标含 file:line、动作、理由）；派遣 `scout` 逐项核验目标的引用安全性；`pruner` 只执行 `scout` 判定为 `SAFE` 的目标，`UNSAFE` 直接放弃，`UNCERTAIN` 转交用户决定，执行后自行验证（构建/lint/测试）。

**这是飞轮在收尾阶段的一次运行，但形态不同**：验证被前置到行动之前——产出 = 清理计划（不是清理结果）；验证 = `scout` 核验计划中每个目标；修正 = 从计划中剔除 `UNSAFE`/`UNCERTAIN` 目标；执行 = 只对核验通过的目标动手，随后 `pruner` 自行做直接验证确认没有破坏行为。因为安全性已经在行动前锁定，执行完成后不再回到 `critic-gate` 复核这一轮。

- 这一步是里程碑式编码工作流的必经环节，不做体量豁免，也不延伸到无里程碑的调查/诊断类任务。
- 清理范围按**文件级**限定在本次任务触及的文件：触及文件内的存量遗留（非本次 diff 引入）同样在范围内——它们留在被触及文件中，同样会随迭代趋向过时；触及文件之外一律不动——那是 `quality-auditor` 的职责。若清理产生实际改动，以单个 chore 提交收束。
- 完整契约见 `subagents/pruner.md` 与 `subagents/scout.md`。
