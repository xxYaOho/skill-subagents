# by Coding

适用场景：深入讨论后先产出草案/方案/计划，再进入实现的编码类任务。

三个阶段串行，每阶段结束默认停住等用户确认；用户明确要求全自动执行（如"不用问我，全部做完再汇报"）时解除停顿。每阶段是一次独立的飞轮运行（原语与修正轮次上限见 `SKILL.md`），下文每阶段只标注一行实例化参数。

## 1. 前期讨论

草案/计划形成后派遣 `critic-strict` 审查，直到 `STATUS: PASS`（0 FATAL）再交用户。

飞轮：产出 = 草案/计划；验证 = `critic-strict`；修正 = 按 FATAL 改稿；停止 = PASS。

### 计划审查阈值

计划必须做出生成性选择（步骤顺序、阶段边界、回退策略、验证方式），这些是草案未覆盖的新假设，是否复审按计划层厚度判断。厚度只看任务属性，与改动规模和 agent 能力无关。

薄计划层（全部满足）可跳过复审，但须一行声明理由，向用户可见、可否决：

- 生成性选择平凡：单阶段、顺序显然、无需定义阶段边界、无回退/迁移/状态编排
- 改动可逆且局部
- 验收标准全部可直接验证
- 上游草案已通过 `critic-strict`（或改动小到无需草案）

任一命中则必须复审：

- 非平凡的阶段边界，或阶段间存在依赖执行顺序
- 计划做出草案留空的关键选择：回退策略、迁移路径、并发模型、验证窗口
- 不可逆或高爆炸半径操作
- 验证不透明（外部运行时、人工验收）
- 计划偏离已审草案——机械触发，不留裁量空间
- 无既有模式可循的新颖地带

### 操作细则

- 分阶段计划必须在实施前定义可验证的里程碑；节点文本自足：验收标准编码对下游的接口承诺，并附下游对本节点的接口依赖——这是派遣 `coder-plus` 的输入要求。审查与判定契约见 `subagents/critic-strict.md`。
- 修正轮次 v1, v2... 不体现在最终文件名中。
- 向用户输出完整最终文档；(可选) 简要说明迭代解决的主要问题。
- **停止，等用户确认是否进入实施。**

### 节点标注

分派判据在计划期一次做完，实施期只执行标注。计划书每个节点显式标注三项：

- 执行形态：`coder-plus`（里程碑节点）/ `coder`（单工作单元）/ `swarm`（同质批量）/ `亲自`（平凡改动，须三条件全满足并一行声明）
- 性质标记：不可逆 / 迁移 / 契约变更 / 验证不透明 / 新颖
- gate 方式：外派 `critic-gate` / 编排者兼任

节点契约字段（派遣输入）：验收标准、可动文件范围、下游接口依赖摘要、性质标记、gate 方式、覆盖的需求编号（若计划含需求层）。

性质轴机械规则（与计划审查阈值同源，镜像进标注）：

- 不可逆或高爆炸半径 → 该节点必须外派 `critic-gate`，无论执行形态。缓解降级（计划期判定）：计划显式声明缓解措施且 critic-strict 确认缓解成立，可改标"编排者兼任"；该 gate 必须包含缓解的直接验证（回退/幂等测试），验证失败或存疑时机械升级外派 `critic-gate`
- 迁移 / 状态编排 / 回退 → 必须标注里程碑节点，派遣 `coder-plus`
- 契约 / 格式变更 → 至少派遣执行代理（不得亲自），下游同步纳入验收
- 验证不透明 → 外派 `critic-gate`
- 新颖地带 → 计划复审

平凡改动三条件（全部满足才可标注"亲自"，并须一行声明理由，向用户可见、可否决）：

- 单文件级（字面单文件，非"单文件主导"）
- 直接可验证
- 不命中任何性质标记

节点粒度下限：独立可验证 + 有决策或契约边界 + 无法无损失合并，三者同时满足才配独立 gate；验证型节点归入前序节点退出条件，同质小改动打包为一个节点。

## 2. 中期实施

以里程碑为单位推进，每个里程碑是一次独立飞轮。

飞轮：产出 = 该节点的实现；验证 = 执行者自验证 + gate；修正 = 按 gate 裁决分流修正；停止 = PASS 且完成原子提交。

### 分派

实施期按计划书节点标注机械派遣，禁止重新分类：

- `coder-plus` 标注 → 每节点一次派遣
- `coder` 标注 → 单体或并行派遣
- `swarm` 标注 → 按 `SKILL.md` 调度分档
- `亲自` 标注 → agent 亲自实施（跳过派遣不豁免 gate）

执行中发现标注与事实不符（如"平凡"节点实际跨多文件或含迁移）→ 停止，回 §1 修正标注，不就地降档、不就地外派；若修正触及性质标记或节点边界，重新走计划审查。

### 派遣纪律

- 每次派遣只交当前节点所需：节点实现内容、验收标准、可动文件范围（里程碑边界）、下游接口依赖摘要。计划全文只存在于 agent——防执行者预支后续节点，也避免重复加载。
- coder-plus 返回 `STATUS: DONE` 后依次收口：复核 VERIFICATION → gate → PASS 后原子提交 → 才派遣下一节点。派遣前可依据上一节点实际结果微调其节点文本。
- 开工后节点文本即权威基线，coder-plus 无中途否决权；实现方式裁量归执行者，偏差必须记入 DEVIATIONS。
- 里程碑边界随计划书在讨论阶段确定，不由执行者临时划分——执行者有把边界划大以减少被检查次数的动机。
- 完整契约见 `subagents/coder-plus.md`。

### gate

gate 只存在于里程碑交付点，每节点一次。coder-plus 内部的原子任务与 leaves 无 gate，只有自验证；单工作单元整单元一次 gate，不内切。

- 实施者 = 子代理 → 编排者亲自 gate（审查他人产出，理由见 `SKILL.md`）
- 实施者 = 编排者本人 → 机械外派 `critic-gate`（自审违反 Fresh Agent 原则）
- 唯一例外：节点标注"平凡改动"且三条件全满足 → gate 退化为直接验证（跑测试、查 diff），不构成 critique

外派 `critic-gate` 的两种情况：

- 节点性质标记命中不可逆 / 验证不透明——机械触发，不留裁量（不可逆节点经缓解降级改标兼任的除外，见 §1 节点标注）
- 其余节点存在直接验证未覆盖的回归、契约或隐藏正确性风险——agent 裁量

gate 对照计划当前节点审查 DEVIATIONS 与 CHANGES：良性偏差（如更优实现）+ 验收满足 + 如实上报 = PASS；偏离验收标准或中途削减范围 = FAIL。外派须提供有效基线，见 `subagents/critic-gate.md`。

FAIL 修正按偏差性质分流：原子性偏差（局部错误）派遣 `coder` 定点修正；结构性偏差（实现路线错误）重派 `coder-plus`。

**原子化提交是里程碑退出条件**：gate PASS 后由 agent 以 Conventional Commits 提交该节点全部改动；用户未要求提交不构成跳过理由，未要求 push（coder-plus 不创建提交）。

全部里程碑完成后向用户汇报：最终结果 +（可选）过程中影响设计决策的重要情况。

## 3. 收尾整理

派遣 `pruner` 清理本次任务触及的文件——必经环节，不做体量豁免；单工作单元任务同样执行 pruner→scout 收尾；不延伸到无里程碑的调查/诊断类任务。

飞轮（验证前置形态）：产出 = 清理计划；验证 = `scout` 逐项核验；修正 = 剔除 `UNSAFE`/`UNCERTAIN` 目标；执行后只做直接验证，不再回 gate。

安全流程由 pruner 自持（起草计划 → 派 `scout` 核验 → 只执行 `SAFE`，`UNSAFE` 放弃，`UNCERTAIN` 转交用户 → 执行后自行验证），契约见 `subagents/pruner.md` 与 `subagents/scout.md`。清理范围按文件级限定在触及文件，含存量遗留；若产生实际改动，以单个 chore 提交收束。
